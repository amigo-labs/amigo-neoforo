# 01 – Datenmodell

Status: lebend · Zuletzt geändert: 2026-10-28 · Gilt für Phasen 0–2

## Konventionen

- Tabellen und Spalten in `snake_case`, Tabellennamen im Plural.
- Primärschlüssel: `id bigint GENERATED BY DEFAULT AS IDENTITY` (siehe E2).
- Zeitstempel: immer `timestamptz`. XenForo speichert Unix-Integer; der Importer konvertiert.
- Benutzernamen und E-Mails: `citext` (Extension `citext`).
- Sichtbarkeit von Inhalten über einen State statt Hard-Delete:
  `content_state AS ENUM ('visible', 'moderated', 'deleted')`.
- Denormalisierte Zähler (Antworten, Posts, letzter Post) werden in derselben Transaktion
  aktualisiert. Für jeden Zähler gibt es einen Rebuild-Job.
- Autorennamen werden an Threads und Posts zusätzlich als `username` gespeichert, damit
  Inhalte gelöschter User lesbar bleiben (wie in XenForo).
- Migrationen über `sqlx migrate`, niemals bestehende Migrationen ändern.
- Migrationen sind rückwärtskompatibel zur Vorversion (Expand/Contract, siehe
  `02-betrieb.md`): erst hinzufügen und befüllen, Entfernen oder Umbenennen frühestens eine
  Version später.
- Fremdschlüssel auf `users`: von Inhalten (Threads, Posts, Anhänge, …) mit
  `ON DELETE SET NULL`, damit Inhalte eine Kontolöschung überstehen (E9); von reinen
  Kontodaten (Profil, Anmeldedaten, Sessions, Passkeys, …) mit `ON DELETE CASCADE`.
- Secrets in der Datenbank (TOTP) werden mit einem Schlüssel verschlüsselt, der per HKDF aus
  dem Instanz-Secret (`NEOFORO_SECRET_KEY`) abgeleitet ist. Gleiches gilt für HMAC-Schlüssel
  (Bild-Proxy, signierte Links, Formular-Zeitstempel). Jeder Zweck bekommt einen eigenen
  abgeleiteten Schlüssel.

## Phase 0/1 – Infrastruktur

### `instances` (Phase 0)
Laufende Prozesse für Überblick und Job-Recovery (siehe `02-betrieb.md`).

| Spalte | Typ | Hinweis |
|---|---|---|
| id | uuid PK | Zufällig beim Prozessstart |
| role | text | `all`, `web`, `worker` |
| hostname | text | |
| version | text | |
| started_at | timestamptz | |
| last_seen_at | timestamptz | Heartbeat alle 15 s, Einträge älter als 1 Tag werden gelöscht |

### `jobs` (Phase 1)
| Spalte | Typ | Hinweis |
|---|---|---|
| id | bigint | |
| kind | text | z. B. `send_mail`, `ip_log_cleanup`, `backup` |
| payload | jsonb | |
| state | enum `queued`, `running`, `done`, `failed` | |
| dedupe_key | text null unique | Für geplante Aufgaben: Aufgabe + Zeitfenster |
| attempts, max_attempts | int | Exponentielles Backoff zwischen Versuchen |
| run_at | timestamptz | |
| locked_by | uuid null → instances | `ON DELETE SET NULL` |
| locked_at | timestamptz null | |
| last_error | text null | |
| created_at, finished_at | timestamptz | |

Index: `(run_at) WHERE state = 'queued'`. Abholen mit `FOR UPDATE SKIP LOCKED`. Erledigte
Jobs werden nach 7 Tagen gelöscht, fehlgeschlagene bleiben bis zur manuellen Freigabe.

### `rate_limits` (Phase 1)
`UNLOGGED`-Tabelle, damit alle Instanzen dieselben Limits sehen. Ein Verlust nach einem
Absturz ist unkritisch.

`key text` (z. B. `login:ip:203.0.113.7`), `window_start timestamptz`, `hits int`,
PK `(key, window_start)`. Aktualisierung per `INSERT … ON CONFLICT DO UPDATE`, Aufräumen per
Job.

## Phase 2 – Inhalte

### `nodes`
Gemeinsame Basis aller Knoten im Baum.

| Spalte | Typ | Hinweis |
|---|---|---|
| id | bigint | |
| parent_id | bigint null → nodes | null = Wurzelebene |
| node_type | enum `category`, `forum`, `link`, `page` | |
| title | text | |
| description | text | BBCode erlaubt |
| display_order | int | |
| display_in_list | bool | |
| path | bigint[] | gecachte Vorfahren-IDs, für Breadcrumbs und Rechtevererbung |

Kein Nested Set (XenForo nutzt `lft`/`rgt`): `parent_id` + `path`-Cache ist einfacher zu
pflegen und reicht für Foren-Baumgrößen. Der Importer übernimmt nur `parent_id` und
`display_order`.

### `forums`
Typspezifische Daten für `node_type = 'forum'`.

| Spalte | Typ |
|---|---|
| node_id | bigint PK → nodes |
| thread_count, message_count | int |
| last_post_id | bigint null |
| last_post_at | timestamptz null |
| last_thread_id | bigint null |
| allow_posting | bool |
| moderate_threads, moderate_replies | bool |

### `threads`
| Spalte | Typ | Hinweis |
|---|---|---|
| id | bigint | |
| node_id | bigint → forums | |
| user_id | bigint null → users | |
| username | text | |
| title | text | Slug wird beim Rendern abgeleitet, nicht gespeichert |
| discussion_type | enum `discussion`, `question`, `poll`, `article`, `suggestion` | Thread-Typen wie in XenForo 2.2+ |

### `posts`
| Spalte | Typ | Hinweis |
|---|---|---|
| id | bigint | |
| thread_id | bigint → threads | |
| user_id | bigint null → users | |
| username | text | |
| position | int | Position der sichtbaren Posts im Thread, Basis für Pagination |
| message | text | BBCode |
| render_cache | text null | gerendertes HTML |
| render_version | int | wird hochgezählt, wenn sich der Renderer ändert → Cache invalid |
| message_state | content_state | |
| created_at | timestamptz | |
| edited_at | timestamptz null | |
| edit_count | int | |
| last_edit_user_id | bigint null | |
| reaction_score | int | |

Index: `(thread_id, position)`. Pagination läuft über `position`, nicht über `OFFSET`.

`render_cache` enthält nur HTML, das für alle Betrachter gleich ist (siehe E1).
Betrachterabhängige Stellen, in Phase 2 die Anhänge, stehen darin als Platzhalter-Elemente
mit ID und werden pro Request ersetzt. Externe Bild-URLs werden erst beim Ausliefern auf den
Bild-Proxy umgeschrieben, damit ein Wechsel des Proxy-Schlüssels den Cache nicht ungültig
macht.

IP-Adressen werden **nicht** an Posts gespeichert, sondern im `ip_log` mit
Aufbewahrungsfrist (siehe E9 und Abschnitt Datenschutz und Spam).

### `thread_views`
`UNLOGGED`, nur `thread_id bigint`. Jeder Aufruf fügt eine Zeile ein, ein Job zählt minütlich
zusammen, erhöht `threads.view_count` und leert die Tabelle. Vermeidet Schreibkonflikte auf
viel gelesenen Threads.

### `polls`, `poll_responses`, `poll_votes`
Für Threads mit `discussion_type = 'poll'`. Phase 2 zeigt Ergebnisse nur an, Abstimmen folgt
in Phase 4.

`polls`: `thread_id bigint PK → threads`, `question text`, `max_votes int` (0 = unbegrenzt),
`public_votes bool`, `change_vote bool`, `view_results_unvoted bool`, `close_at timestamptz null`,
`voter_count int`

`poll_responses`: `id`, `thread_id → polls`, `response text`, `display_order int`,
`vote_count int`

`poll_votes`: `(response_id, user_id)` als PK, `voted_at timestamptz`

### `bb_codes`
Eigene BBCodes (siehe E1). Werden vom Renderer beim Start geladen. Eine Änderung zählt
`render_version` hoch.

| Spalte | Typ | Hinweis |
|---|---|---|
| tag | text PK | Kleingeschrieben, darf kein eingebautes Tag überschreiben |
| title | text | |
| template | text | HTML mit `{text}` und `{option}`, Werte werden escaped eingesetzt |
| has_option | enum `no`, `optional`, `required` | |
| option_regex | text null | Validierung der Option, sonst wird das Tag als Text ausgegeben |
| allow_nested | bool | Ob innerhalb des Tags weiter geparst wird |
| active | bool | |

Das Template wird beim Speichern gegen eine HTML-Whitelist geprüft (keine `script`-Tags,
keine Event-Attribute, keine `style`-Attribute, URLs nur `http`/`https`).

### `attachment_data` und `attachments`
Dedupliziert über den Inhalts-Hash.

`attachment_data`: `id`, `sha256 bytea unique`, `file_size`, `mime_type`, `width`, `height`,
`storage_key`, `created_at`

`attachments`: `id`, `data_id → attachment_data`, `post_id → posts null`, `user_id`,
`filename`, `view_count`, `created_at`

Phase 2 zeigt importierbare Anhänge nur an. Upload folgt in Phase 4.

## Rechte (Struktur, Umsetzung Phase 4)

Bereits jetzt festgelegt, damit das Schema dazu passt:

- `permissions`: `id text PK` (z. B. `forum.view`, `forum.post_reply`), `group text`,
  `value_type` (`flag` oder `integer`)
- `permission_entries`: global pro Gruppe oder User
- `node_permission_entries`: pro Knoten, Gruppe oder User; zusätzlich Wert `reset`
  (Vererbung vom Elternknoten abschneiden), wie in XenForo
- `permission_cache`: berechnete effektive Rechte pro Gruppen-Kombination und Knoten

## Datenschutz und Spam

`ip_log` und `spam_log` kommen in Phase 1, weil die Registrierung die ersten Einträge
schreibt. Die übrigen Tabellen folgen in Phase 4.

### `ip_log`
| Spalte | Typ | Hinweis |
|---|---|---|
| id | bigint | |
| user_id | bigint null → users | `ON DELETE CASCADE` |
| ip | inet | |
| action | text | `register`, `login`, `post`, `thread`, `edit`, … |
| content_type, content_id | text null, bigint null | |
| created_at | timestamptz | |

Index auf `(user_id, created_at)` und `(ip)`. Ein Job löscht Einträge älter als die
Aufbewahrungsfrist (Standard 30 Tage).

### `spam_rules`
`id`, `pattern text`, `is_regex bool`, `action` enum `moderate`/`reject`, `applies_to text[]`
(`post`, `thread_title`, `signature`, `profile`), `active bool`, `created_at`

### `spam_log`
`id`, `user_id null → users (ON DELETE SET NULL)`, `action text` (`register`, `post`, …),
`result` enum `allowed`/`moderated`/`rejected`, `reasons jsonb` (welche Prüfungen
angeschlagen haben), `created_at`. Gleiche Aufbewahrungsfrist wie `ip_log`.

### `spam_cleanups`
`id`, `user_id`, `moderator_id`, `actions jsonb` (betroffene Inhalte mit vorherigem State,
für das Rückgängigmachen), `created_at`, `undone_at timestamptz null`. Rückgängigmachen ist
30 Tage lang möglich.

### `data_exports`
`id`, `user_id → users (ON DELETE CASCADE)`, `state` enum `pending`/`ready`/`failed`,
`storage_key text null`, `created_at`, `expires_at`. Ein Job löscht abgelaufene Exporte
samt Datei.

## Import-Infrastruktur (Phase 3)

- `import_runs`: `id`, `source`, `started_at`, `finished_at`, `stats jsonb`, `report jsonb`
- `import_map`: `(content_type, old_id) → new_id` nur für Fälle, in denen IDs nicht 1:1
  übernommen werden können

## Offen

- Präfixe, Tags, Lesemarkierungen, Abos, Ignorierlisten, Benachrichtigungen, Unterhaltungen,
  Profilposts, Reaktionstypen, Votes für `suggestion`-Threads, verknüpfte Konten: eigene
  Spec-Abschnitte vor der jeweiligen Phase. Der Importer muss diese Daten übernehmen können (siehe Migrationsanforderungen in 00-vision).
