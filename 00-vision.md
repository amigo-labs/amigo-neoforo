# 00 – Vision & Grundsatzentscheidungen

Status: lebend · Zuletzt geändert: 2026-10-28

## Was ist Neoforo?

Neoforo ist eine klassische Forensoftware (Kategorien → Foren → Threads → Posts) in Rust mit
PostgreSQL und htmx. Zielgruppe sind Betreiber bestehender Communitys, insbesondere
**XenForo-Admins, die ohne Verluste umziehen wollen**.

Leitsatz: *Ein Forum, das sich für Nutzer wie XenForo anfühlt, für Admins einfacher zu
betreiben ist und eine ganze Klasse von Sicherheitslücken gar nicht erst haben kann.*

## Ziele

1. **Verlustfreie Migration von XenForo 2.2/2.3:** Passwörter funktionieren weiter, alle Links
   bleiben gültig, Inhalte inklusive Zitaten, Anhängen und eigener BBCodes bleiben erhalten.
2. **Ein Binary + Postgres:** Betrieb ohne PHP, ohne Redis, ohne Message-Broker. Klein auf
   einem Server, groß horizontal skaliert, mit demselben Binary.
3. **Schnell und SEO-freundlich:** serverseitig gerendertes HTML, Grundfunktionen ohne
   JavaScript, saubere kanonische URLs.
4. **Sicher by default:** Memory Safety durch Rust, BBCode als Whitelist-Format, strikte CSP,
   argon2id, Zwei-Faktor-Anmeldung und Passkeys, Spam-Abwehr ab Werk.
5. **Datenschutz by default:** DSGVO-konform ohne Zusatz-Plugins: keine Drittanbieter-Requests,
   keine Tracking-Cookies, Datensparsamkeit, Export und Löschung per Klick.
6. **Zweisprachig ab Start:** Deutsch und Englisch.

## Nicht-Ziele (vorerst)

- Föderation (ActivityPub), native Mobile-Apps
- SPA-Frontend
- Andere Datenbanken als PostgreSQL
- Multi-Tenant/SaaS-Betrieb mehrerer Foren in einer Instanz
- Import aus XenForo 1.x, vBulletin, phpBB (später möglich, nicht im Fokus)

## Stack

| Bereich | Wahl |
|---|---|
| Sprache | Rust, Edition 2024 |
| Web | Axum |
| Templates | Askama |
| Interaktivität | htmx 4, Editor als einzelnes JS-Island (Tiptap) |

| i18n | fluent-rs (de, en) |
| Lizenz | AGPL-3.0 |

## Grundsatzentscheidungen

### E1 – BBCode ist das einzige Inhaltsformat
Posts werden als BBCode gespeichert. Parser und Renderer liegen in `neoforo-core`.
Begründung: verlustfreier XenForo-Import, keine Mischformate (Zitate, Bearbeitung, Suche),
forenspezifische Tags (Zitat mit Post-Referenz, Anhang, Spoiler, Medien) sind etabliert,
Whitelist statt rohem HTML. Der Editor (Tiptap) serialisiert nach BBCode; Markdown-Kürzel
im Editor sind reine Eingabehilfe.

Eigene BBCodes (in XenForo vom Admin angelegt) werden unterstützt, aber nur als
Ersetzungs-Templates mit Platzhaltern (`{text}`, `{option}`), deren Werte immer escaped
eingesetzt werden. Eigene BBCodes, die in XenForo PHP-Callbacks nutzen, sind nicht
übertragbar. Sie bleiben als Text erhalten und werden im Importbericht gelistet.

Gerenderte Posts werden gecacht. Der Cache enthält ausschließlich HTML, das für alle
Betrachter gleich ist. Teile, die vom Betrachter abhängen (z. B. Anhänge abhängig vom
Recht, sie zu sehen), werden als Platzhalter gecacht und erst beim Ausliefern ersetzt. So
kann der Cache keine Inhalte an Unberechtigte ausliefern.

### E2 – IDs sind `bigint`, XenForo-IDs werden 1:1 übernommen
Alle Primärschlüssel sind `bigint GENERATED BY DEFAULT AS IDENTITY`. `BY DEFAULT` erlaubt
explizite IDs beim Import; danach werden die Sequenzen hochgesetzt.

### E3 – URL-Schema wie XenForo
- `/forums/{slug}.{id}/`, `/threads/{slug}.{id}/`, `/threads/{slug}.{id}/page-{n}`
- `/posts/{id}/` → Redirect auf Thread-Seite + Anker
- `/members/{name}.{id}/`
- Der Slug ist kosmetisch: Maßgeblich ist die ID, falscher Slug → 301 auf kanonische URL.
- `/index.php?…` (XenForo ohne Friendly URLs) wird ausschließlich per 301 auf die neuen URLs
  umgeleitet. Intern existiert dieses Schema nicht.
- Weitere extern verlinkte XenForo-URLs werden ebenfalls per 301 umgeleitet bzw. direkt
  bedient. Dazu gehören mindestens `/attachments/{slug}.{id}/`, `/goto/post?id=…`,
  `/threads/{slug}.{id}/post-{id}`, `/forums/{slug}.{id}/index.rss` und `/forums/-/index.rss`.
  Für Funktionen, die es in Neoforo noch nicht gibt (z. B. Tags), liefert die URL 410 statt 404, damit
  Suchmaschinen sie gezielt entfernen.

### E4 – Rechtemodell nach XenForo-Vorbild
Berechtigungen werden Benutzergruppen (und in Ausnahmefällen einzelnen Usern) zugewiesen und
können pro Knoten überschrieben werden. Werte: `allow`, `unset`, `never`. `never` schlägt
alles. Effektive Rechte werden berechnet und gecacht. Die Auswertung ist reine Logik in
`neoforo-core` und ohne Datenbank testbar.

### E5 – Passwörter
Neue Hashes: argon2id. Zusätzlich werden XenForo-Hashformate (bcrypt aus XF 2, ältere Schemata
aus XF 1 bzw. importierten Foren) beim Login geprüft und nach erfolgreichem Login still auf
argon2id umgehasht. Kein erzwungener Passwort-Reset nach Migration.

### E6 – Nur PostgreSQL
Keine Datenbank-Abstraktion. Postgres-Features (citext, Volltextsuche, `LISTEN/NOTIFY`,
`SKIP LOCKED`) werden bewusst genutzt.

### E7 – Clean-Room gegenüber XenForo
XenForo ist proprietär. Das Datenbankschema einer Installation wird gelesen, aber kein Code
von XenForo übernommen oder portiert (auch nicht BBCode-Parser oder Importer).

### E8 – Keine Drittanbieter-Requests ohne Zustimmung
Beim Lesen eines Forums lädt der Browser nur Ressourcen von der eigenen Instanz (DSGVO,
passt zur strikten CSP). Externe Bilder aus `[img]` laufen über einen eingebauten
Bild-Proxy mit HMAC-signierten URLs. Eingebettete Medien aus `[media]` (YouTube usw.) werden
als Platzhalter gerendert und erst nach Klick geladen (2-Klick-Lösung).

### E9 – Datensparsamkeit und Betroffenenrechte
- **Cookies:** nur technisch notwendige (Session, CSRF, Sprache). Kein Tracking, keine
  Analyse-Skripte von Dritten. Damit ist kein Cookie-Banner nötig.
- **IP-Adressen:** nie an Inhalten, sondern im `ip_log` mit Aufbewahrungsfrist (Standard
  30 Tage, konfigurierbar). Ein Job löscht abgelaufene Einträge. Sessions speichern keine IP.
- **Uploads:** Bilder (Anhänge, Avatare) werden serverseitig neu kodiert. Dabei werden alle
  Metadaten (EXIF inkl. GPS, XMP, IPTC) entfernt, die Ausrichtung aus EXIF wird vorher
  angewendet. Das Original wird nicht gespeichert.
- **Datenexport (Art. 15/20):** Jeder Nutzer kann im Konto einen Export anfordern. Ein Job
  erzeugt ein ZIP mit maschinenlesbarem JSON (Konto, Profil, eigene Inhalte, Reaktionen,
  Sessions, IP-Log-Einträge, später Unterhaltungen) und den eigenen Dateien. Download über
  einen signierten Link, der nach 7 Tagen verfällt, Benachrichtigung per E-Mail.
- **Kontolöschung (Art. 17):** vom Nutzer selbst auslösbar (Bestätigung mit Passwort bzw.
  Passkey) oder durch Admins. Gelöscht werden Konto, Profil, Anmeldedaten, Sessions,
  Zwei-Faktor-Daten, Passkeys, IP-Log, Avatar und Exporte. Eigene Beiträge bleiben im
  Forum erhalten, die Verknüpfung zum Konto wird getrennt (`user_id = NULL`). Der
  gespeicherte Autorenname bleibt entweder erhalten oder wird durch „Gelöschter Nutzer
  {id}“ ersetzt. Das entscheidet der Admin global. Zitate in Beiträgen anderer werden nicht
  verändert.
- **Rechtstexte:** Impressum und Datenschutzerklärung sind Knoten vom Typ `page` (bis dahin
  konfigurierte URLs) und werden im Footer verlinkt. Die Datenschutzerklärung muss bei der
  Registrierung bestätigt werden. Die Version wird gespeichert.

### E10 – Spam-Abwehr ohne Drittanbieter
Spam-Abwehr ist eingebaut und standardmäßig aktiv. Sie funktioniert ohne externe Dienste;
CAPTCHAs von Drittanbietern (reCAPTCHA, hCaptcha) gibt es nicht.

- **Registrierung:** Honeypot-Feld, Mindestzeit zwischen Formularaufruf und Absenden
  (signierter Zeitstempel im Formular), Rate-Limit pro IP, E-Mail-Bestätigung, optionale
  Sperrliste für Wegwerf-E-Mail-Domains. Optional und standardmäßig aus: eine selbst
  gehostete Proof-of-Work-Prüfung (eigenes JS, wird ohne JS durch Moderation der
  Registrierung ersetzt).
- **Neue Nutzer:** Bis zu einer konfigurierbaren Zahl freigegebener Beiträge (Standard: 1)
  werden Beiträge moderiert. Bis zu einer weiteren Schwelle (Standard: 5) sind Links in
  Beiträgen und Signatur sowie externe Bilder gesperrt bzw. werden moderiert.
- **Inhaltsregeln:** Admin-pflegbare Regeln (Wort oder Regex) mit Aktion `moderate` oder
  `reject`. Gilt für Beiträge, Thread-Titel, Signaturen und Profilfelder.
- **Spam-Bereinigung:** Moderatoren entfernen einen Spammer in einem Schritt: Konto sperren,
  alle Beiträge und eigenen Threads soft-löschen, IP-Adressen aus dem `ip_log` anzeigen.
  Jede Bereinigung landet im Audit-Log und lässt sich innerhalb von 30 Tagen rückgängig
  machen.
- **Externe Prüfdienste** (z. B. StopForumSpam) sind optional und standardmäßig aus, weil
  dabei E-Mail und IP an Dritte gehen. Sind sie aktiv, steht das in der
  Datenschutzerklärung-Vorlage.
- Jede Spam-Entscheidung wird im `spam_log` protokolliert (Admin-Ansicht, gleiche
  Aufbewahrungsfrist wie das `ip_log`).

### E11 – Zwei-Faktor-Anmeldung und Passkeys
- **TOTP** (RFC 6238) als zweiter Faktor, dazu 10 Wiederherstellungscodes (nur als Hash
  gespeichert). TOTP-Secrets aus XenForo werden übernommen, sofern lesbar (siehe
  Migrationsanforderungen).
- **Passkeys** (WebAuthn) sind sowohl zweiter Faktor als auch passwortlose Anmeldung. Ein
  Nutzer kann mehrere Passkeys registrieren und benennen.
- TOTP-Secrets werden in der Datenbank verschlüsselt gespeichert (AEAD, Schlüssel aus dem
  Instanz-Secret abgeleitet).
- Admins und Moderatoren können per Gruppeneinstellung zur Zwei-Faktor-Anmeldung
  verpflichtet werden.
- Neue Anmeldungen und Änderungen an Anmeldedaten (Passwort, E-Mail, zweiter Faktor) werden
  per E-Mail gemeldet.

### E12 – Betrieb: ein Binary, mehrere Rollen
Betriebswerkzeuge sind Teil des Binarys, kein separates Programm.

- **Rollen:** `neoforo serve --role all|web|worker`. Standard ist `all` (ein Prozess).
  Größere Installationen starten denselben Binary getrennt als `web` (HTTP) und `worker`
  (Job-Queue, geplante Aufgaben wie Backups und Aufräum-Jobs). Mehrere `web`-Prozesse
  hinter einem Load-Balancer sind möglich, weil aller Zustand in Postgres liegt.
- **`neoforo doctor`:** prüft Konfiguration, Instanz-Secret, Datenbankverbindung und
  -version, ausstehende Migrationen, Storage (Lesen, Schreiben, Löschen), Mailversand
  (optional Testmail), Zeitabweichung, verfügbare `pg_dump`-Version und das Alter des
  letzten erfolgreichen Backups. Ausgabe lesbar oder als JSON, Exit-Code ≠ 0 bei Fehlern.
  Die gleichen Prüfungen erscheinen als Admin-Seite.
- **Metriken:** Prometheus-Format unter `/metrics` auf einem eigenen Listener
  (`NEOFORO_METRICS_ADDR`, Standard `127.0.0.1:9100`), nie auf dem öffentlichen Port.
  Mindestens: HTTP-Requests nach Route und Status, Latenzen, DB-Pool, Job-Queue (wartend,
  laufend, fehlgeschlagen, Alter des ältesten Jobs), Render-Cache-Trefferquote,
  Bild-Proxy, Spam-Entscheidungen, Zeitpunkt des letzten Backups. `/health` bleibt
  öffentlich und minimal (`ok` oder `503`).
- **Backup:** `neoforo backup` erzeugt ein Archiv aus Datenbank-Dump (`pg_dump`
  Custom-Format) und Storage-Inhalt (beim `fs`-Backend die Dateien; beim `s3`-Backend
  optional, da S3 meist eigene Versionierung hat) plus Manifest (Neoforo-Version,
  Migrationsstand, Prüfsummen). Ziel: lokales Verzeichnis oder S3. Optional verschlüsselt
  (age). Geplante Backups laufen als Job in der `worker`-Rolle, mit Aufbewahrungsregel
  (Standard: 7 tägliche, 4 wöchentliche). Das Instanz-Secret ist bewusst **nicht** im
  Backup; ohne es sind TOTP-Secrets unbrauchbar. `doctor` und die Admin-Seite weisen darauf
  hin.
- **Restore:** `neoforo restore <archiv>` nur bei gestopptem Server oder im Wartungsmodus.
  Prüft Manifest und Prüfsummen, lehnt Backups neuerer Neoforo-Versionen ab, spielt Dump
  und Dateien ein und führt danach ausstehende Migrationen aus. `--verify` stellt in eine
  temporäre Datenbank wieder her und prüft nur, ohne die laufende Instanz zu berühren.
- Das Docker-Image enthält `pg_dump`/`pg_restore` passend zur unterstützten Postgres-Major.
- Konfiguration, CLI-Referenz und Hosting-Varianten: `02-betrieb.md`.

### E13 – Horizontal skalierbar
Die `web`-Rolle ist zustandslos und lässt sich beliebig oft hinter einem Load Balancer
starten, ohne Sticky Sessions. Mehrere `worker` sind möglich; geplante Aufgaben laufen
trotzdem genau einmal. Postgres ist die einzige Quelle für geteilten Zustand und
Prozess-Kommunikation (`LISTEN/NOTIFY`), Dateien liegen dann im S3-Storage. Updates laufen
als Rolling Update ohne Downtime, deshalb sind Migrationen rückwärtskompatibel zur
Vorversion. Die verbindlichen Regeln für den Code stehen in `02-betrieb.md`
(Skalierungsregeln).

### E14 – SEO
Suchmaschinen sind die wichtigste Besucherquelle von Foren. Ein Umzug darf kein Ranking kosten
(siehe E3), und neue Inhalte sollen schnell gefunden werden.

- **Kanonische URLs** auf jeder Seite, jede Pagination-Seite ist selbstkanonisch. Seiten mit
  Filter- oder Sortierparametern verweisen auf die Version ohne Parameter.
- **`sitemap.xml`** als Index mit Teil-Sitemaps zu je höchstens 50.000 URLs (Foren, Threads
  mit `lastmod`, öffentliche Profile mit Inhalten). Sie wird als Job erzeugt und im Storage
  abgelegt, nicht pro Request berechnet. Enthalten ist nur, was Gäste sehen dürfen.
- **`robots.txt`** aus einer Vorlage, im Admin-Bereich änderbar, verweist auf die Sitemap.
- **Meta-Daten:** `<title>` und `meta description` (aus dem ersten Beitrag, BBCode
  entfernt, ca. 160 Zeichen), OpenGraph und Twitter Cards (Vorschaubild: erstes Bild bzw.
  Anhang des Threads, sonst Forenlogo).
- **Strukturierte Daten (JSON-LD):** `DiscussionForumPosting` mit Kommentaren und
  Interaktionszahlen für Threads, `BreadcrumbList`, `ProfilePage` für Profile,
  `QAPage` für Threads vom Typ `question` mit markierter Lösung.
- **Feeds:** RSS 2.0 und Atom pro Forum und für das gesamte Forum (auch unter den
  XenForo-URLs aus E3).
- **`noindex`** für Seiten ohne eigenen Inhalt: Suche, Login, Registrierung, leere Profile,
  Mitgliederlisten.
- **Statuscodes:** gelöschte Threads liefern Gästen 410, verschobene Threads 301 auf die neue
  URL (Thread-ID bleibt gleich, nur das Forum ändert sich, daher genügt die kanonische
  Weiterleitung). Moderierte Inhalte liefern Gästen 404.
- **Performance als Ranking-Faktor:** Bilder und Anhänge haben `width`/`height` (keine
  Layout-Verschiebung), `loading="lazy"` ab dem dritten Bild, kein render-blockierendes JS.
- **Optional:** IndexNow-Ping bei neuen Threads (standardmäßig aus; es werden nur URLs
  übermittelt, keine personenbezogenen Daten).

### E15 – Themes
Askama-Templates werden zur Compile-Zeit übersetzt und lassen sich zur Laufzeit nicht
austauschen. Themes ändern deshalb das Aussehen, nicht die HTML-Struktur.

- **Design-Tokens:** Das Basis-Layout nutzt ausschließlich CSS Custom Properties (Farben,
  Schriften, Abstände, Radien, Breiten). Ein Theme ist ein Satz Token-Werte.
- **Eigenes CSS:** pro Theme zusätzlich frei definierbares CSS, als eigene Datei mit
  Inhalts-Hash ausgeliefert (kein Inline-CSS, CSP bleibt strikt). `url()` auf externe Hosts
  blockiert die CSP (E8).
- **Assets:** Logo, Favicon, App-Icons, Vorschaubild für OpenGraph, Schriften (selbst
  gehostet) liegen im Storage.
- **Hell und dunkel:** Jedes Theme hat Token-Sätze für hell und dunkel. Standard folgt
  `prefers-color-scheme`, Nutzer können umschalten (Cookie bzw. Konto-Einstellung,
  funktioniert ohne JS).
- **Vererbung:** Ein Theme kann von einem anderen erben und nur einzelne Tokens
  überschreiben.
- **Auswahl:** Admins legen ein Standard-Theme fest und können weitere für Nutzer
  freigeben.
- **Paketformat:** ZIP mit `theme.toml` (Name, Version, Eltern-Theme, Tokens), `custom.css`
  und Assets. Import und Export im Admin-Bereich.
- **XenForo:** Der Importer übernimmt aus den Style-Properties des Standard-Styles Farben,
  Logo und Favicon als Ausgangs-Theme. Templates und Less-Code werden nicht übernommen (E7).
- Strukturelle Anpassungen (zusätzliche Blöcke in Header, Footer oder Seitenleiste) laufen
  über Layout-Slots, die Admins mit BBCode befüllen, nicht über Template-Overrides.

### E16 – Webhooks
Webhooks sind die erste und wichtigste Integrationsschnittstelle, vor Plugins.

- **Ereignisse** (Auswahl pro Webhook): `thread.created`, `thread.updated`, `thread.deleted`,
  `post.created`, `post.updated`, `post.deleted`, `user.registered`, `user.updated`,
  `report.created`, `moderation.queued`, `chat.message.created`. Die Liste wächst mit den
  Funktionen.
- **Format:** JSON mit versioniertem Schema (`"schema": 1`), Ereignis-ID, Zeitpunkt und den
  betroffenen Objekten (inkl. kanonischer URL und gerendertem HTML bei Inhalten).
- **Signatur:** nach der Spezifikation „Standard Webhooks“ (Header `webhook-id`,
  `webhook-timestamp`, `webhook-signature`, HMAC-SHA256), damit Empfänger vorhandene
  Bibliotheken nutzen können. Das Secret wird verschlüsselt gespeichert.
- **Rechte:** Ein Webhook sieht standardmäßig nur, was Gäste sehen dürfen. Der Admin kann
  eine Benutzergruppe wählen, deren Rechte gelten sollen (z. B. für Moderations-Ereignisse).
- **Zustellung** über die Job-Queue: Das Ereignis wird in derselben Transaktion wie die
  Änderung als Job angelegt (Transactional Outbox, kein Ereignis geht verloren). Timeout
  10 s, Retry mit exponentiellem Backoff bis 24 h. Nach 50 aufeinanderfolgenden Fehlern wird
  der Webhook deaktiviert und der Admin per E-Mail informiert.
- **SSRF-Schutz:** nur `https` (`http` nur mit expliziter Freigabe), keine privaten oder
  internen Zieladressen, außer der Admin erlaubt sie ausdrücklich pro Webhook.
- **Protokoll:** Zustellungen mit Statuscode und Antwortauszug für 14 Tage, im Admin-Bereich
  einsehbar, einzelne Zustellungen erneut auslösbar, Test-Ereignis per Knopfdruck.

### E17 – Chat
Echtzeit-Chat in Räumen, ergänzend zu Threads (dauerhaft, durchsuchbar) und Unterhaltungen
(privat, asynchron).

- **Räume sind Knoten** vom Typ `chat`. Damit gelten Baum, Breadcrumbs und das Rechtemodell
  (E4) unverändert, z. B. ein Raum nur für Moderatoren über Knotenrechte. Rechte:
  `chat.view`, `chat.post`, `chat.moderate`.
- **Nachrichten** sind BBCode mit eingeschränktem Tag-Set (`b i u s`, `url`, `icode`,
  `ispoiler`, `user`; Emojis als Unicode). Bearbeiten und Löschen der eigenen Nachricht ist kurz nach dem
  Senden möglich (Standard: 5 Minuten).
- **Echtzeit:** Senden per htmx-`POST`, Empfang per SSE. Die schreibende Instanz sendet
  `NOTIFY` mit Raum- und Nachrichten-ID (nie den Inhalt, wegen der Grenze von 8 KB pro
  Payload). Jede `web`-Instanz lädt die Nachricht einmal und verteilt sie an ihre
  verbundenen Clients (siehe Skalierungsregeln). Nach einem Verbindungsabbruch holt der
  Client verpasste Nachrichten über `Last-Event-ID` nach.
- **Ohne JavaScript:** Der Raum ist eine normale Seite mit Formular, neue Nachrichten
  erscheinen nach dem Neuladen.
- **Anwesenheit:** Wer gerade im Raum ist, ergibt sich aus offenen SSE-Verbindungen und wird
  instanzübergreifend in einer `UNLOGGED`-Tabelle mit Heartbeat geführt.
- **Moderation:** Nachrichten löschen, Nutzer pro Raum oder global stummschalten (mit
  Ablaufzeit), Melden wie bei Beiträgen. Spam-Abwehr (E10) gilt: Rate-Limit, Inhaltsregeln,
  Link-Sperre für neue Nutzer.
- **Datenschutz:** Aufbewahrungsfrist pro Raum (Standard 90 Tage, `0` = unbegrenzt), ein Job
  löscht ältere Nachrichten. Chatnachrichten sind Teil von Datenexport und Kontolöschung
  (E9).
- **SEO:** Chaträume sind `noindex` und nicht in der Sitemap.
- **Nicht im Umfang:** Sprach- und Videochat, Datei-Uploads im Chat, Ende-zu-Ende-
  Verschlüsselung, private 1:1-Chats (dafür gibt es Unterhaltungen, die ebenfalls live
  aktualisiert werden).

## Migrationsanforderungen (Kurzfassung)

Ausführlich in einer eigenen Spec (`03-xenforo-import.md`) vor Phase 3.

- Quelle: MySQL-Datenbank von XenForo direkt + Dateisystem (`internal_data/attachments`,
  `data/avatars`). Nicht die REST-API.
- Reihenfolge: Gruppen → User inkl. Profilen → Knoten → Threads → Posts → Umfragen →
  Anhänge/Avatare → Reaktionen → Unterhaltungen → Nutzerzustand → Rechte.
- Eigene BBCodes werden vor den Posts übernommen (siehe E1).
- Farben, Logo und Favicon des Standard-Styles werden als Ausgangs-Theme übernommen (E15).
- Daten aus Chat-Add-ons (z. B. Siropu Chat) werden im Bericht gelistet. Ein Import ist
  vorerst nicht geplant.
- Nutzerzustand umfasst beobachtete Threads und Foren, Ignorierlisten, Lesemarkierungen,
  Zwei-Faktor-Einstellungen und verknüpfte Konten (z. B. Google-Login). Was davon nicht
  übernommen werden kann, steht im Bericht.
- Probelauf mit Bericht über nicht übernommene Daten, wiederholbar, finaler Delta-Import vor
  der Umstellung. Während des finalen Imports läuft Neoforo im Wartungsmodus (nur Admins
  haben Zugriff).
- Nicht abbildbare Rechte und Add-on-Daten werden im Bericht gelistet, nie stillschweigend
  verworfen.
- Link-Prüfung als Teil des Berichts: Eine Liste alter URLs (aus der Sitemap der alten
  Installation oder aus Zugriffslogs) wird gegen Neoforo geprüft. Jede alte URL muss 200,
  301 oder bewusst 410 liefern.

## Qualitätsziele

- CI: `cargo fmt --check`, `cargo clippy -- -D warnings`, Tests gegen echtes Postgres,
  `cargo sqlx prepare --check`, `cargo deny`.
- Thread-Seite (20 Posts, Render-Cache warm): Server-Antwort < 20 ms auf Entwickler-Hardware.
- Alle Seiten zum Lesen funktionieren ohne JavaScript.
- Commits nach Conventional Commits.
